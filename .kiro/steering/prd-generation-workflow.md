# PRD 生成工作流规范

## 工作流定位

PRD（产品需求文档）是 MRD 的下游文档，面向 ETL 开发人员，目标是将 MRD 中的业务需求转化为可执行的开发规格说明。PRD 的信息来源于：
1. **MRD 文档**（主要来源，可直接转换的内容）
2. **系统数据收集**（需线下确认的内容，如表名、字段名、SQL 逻辑等）

## 输出路径规范

- **PRD 生成文档**统一输出到飞书 Wiki，不再生成本地 .md 文件
- **PRD 评审结果文档**统一输出到：`虾兵/PRD评审结果/` 目录下
- PRD 生成文件命名格式（飞书文档标题）：`开发文档-PRD-{公司/事业部}-【{板块}】-【{指标名称}】`
- PRD 评审文件命名格式：`{原PRD文件名}-评审优化版.md`

## 飞书输出规范

### PRD 模版来源
- PRD 模版从飞书在线文档获取，命令：
  ```bash
  lark-cli docs +fetch --doc "https://hisense.feishu.cn/wiki/QqbKwXkBsiXT69k8dyZcBT5qnzf" --api-version v2 --as user --format pretty
  ```
- **严禁修改模版文档**，只能读取参考其结构

### PRD 文档创建位置
- **优先**：在用户提供的 MRD 飞书链接下面创建子文档（需要先获取 MRD 的 node_token）
- **备用**（无权限时）：在 PRD 节点下创建子文档，parent_node_token 为 `Qf36wn4aRig8DkkTIUFcToV2nnc`
- space_id：`7497785984860553218`

### 创建飞书文档命令
```bash
# 第一步：获取 MRD 文档的 wiki node 信息
lark-cli wiki +node-get --node-token "<MRD飞书链接>" --as user --format pretty

# 第二步：在 MRD 节点下创建 PRD 子文档
lark-cli wiki +node-create --title "开发文档-PRD-{公司}-【{板块}】-【{指标名称}】" --parent-node-token "<MRD的node_token>" --space-id "7497785984860553218" --as user

# 如果上面报权限错误，则用备用位置：
lark-cli wiki +node-create --title "开发文档-PRD-{公司}-【{板块}】-【{指标名称}】" --parent-node-token "Qf36wn4aRig8DkkTIUFcToV2nnc" --space-id "7497785984860553218" --as user

# 第三步：用 v2 API 写入内容（必须用 v2，v1 会丢失图片）
lark-cli docs +update --doc "<新文档的obj_token>" --api-version v2 --as user --command overwrite --content @./临时文件.md --doc-format markdown
```

### 注意事项
- 所有 lark-cli 命令必须加 `--as user` 参数
- markdown 内容如果太长，可以先写入临时文件再用 `@file` 引用：`--markdown @/tmp/prd_content.md`
- 创建文档后在聊天中告知用户飞书文档链接

## 触发条件

当用户要求"写 PRD"、"生成 PRD"、"MRD 转 PRD"或提供 MRD 文档（飞书链接或 .md 文件）要求生成对应 PRD 时，按本工作流执行。

## 执行流程

1. 读取对应的 MRD 文档：
   - 如果用户提供飞书链接：用 `lark-cli docs +fetch --doc "<链接>" --api-version v2 --as user --format pretty` 读取
   - 如果用户提供 .md 文件路径：直接读取本地文件
2. 读取飞书 PRD 模版作为结构参考（不修改模版）
3. 按 PRD 模版结构逐章节提取和转换信息
4. 对于无法从 MRD 获取的信息（如具体表名、字段名、SQL 逻辑），标注为"待系统人员确认"
5. 将 PRD 内容创建为飞书新文档（按飞书输出规范执行）
6. 在聊天中告知用户新文档的飞书链接

## PRD 模版结构与填写规则

### 版本信息表

文件开头插入版本控制表：
```markdown
| **版本号** | **更新日期** | **修订人** | **变更描述简介** |
| ------- | ---------- | ------- | ---------- |
| 1.0     | YYYY/MM/DD | liyingqi1 | 建立         |
```

**文档更新规则：** 每次更新PRD文档时，版本号递增（1.0→2.0→3.0...），在版本记录表中新增一行，写清楚本次变更了什么内容。

### 一、需求基础信息

#### 1. 需求提出人/部门
- **来源**：MRD 的需求提出人信息
- **格式**：XXX公司--XXX部门--需求提出人
- **严格规则**：只能从 MRD 文档中明确写出的信息提取，MRD 没写公司名就不加公司名，不能从其他文档或上下文推断。如果 MRD 只写了修订人和部门，就只写"部门--姓名"。
- **⚠️ 部门查询（强制执行，不可跳过）**：生成PRD时**必须**用 `lark-cli contact +search-user --query "姓名" --as user` 查询需求提出人的完整组织架构（返回的 `department` 字段），将查询到的部门信息填入PRD。**绝对不能只写姓名不写部门。** 如果查询失败或无结果，则在姓名后标注"（⚠️部门待确认）"。

#### 2. 业务背景
- **来源**：直接复制 MRD 的【1.1 需求背景/痛点】
- **处理**：原文复制，不做改写

#### 3. 产品目标（可量化）
- **来源**：直接复制 MRD 的【1.3 预期收益/价值评估】
- **处理**：原文复制，不做改写

#### 4. 关联文档
- **来源**：MRD 文档链接 + 需求编号
- **格式**：
```markdown
> * 《MRD》链接：[MRD文档名称](链接)
> * 《MRD》需求评审登记链接：[01 数据产品需求池](https://hisense.feishu.cn/wiki/ABw2wuqRKiuiG7kKa2ccZxSznse?fromScene=spaceOverview&table=tblvTFKWyhK5QbQs&view=vew5wSiQtW)，需求编号：待填写
```

### 二、数据定义

#### 1. 指标探源
- **来源**：MRD 的指标定义、计算公式、数据来源系统
- **格式**：表格形式，包含以下列：
  - 指标名称：从 MRD 指标名称提取
  - 指标是否已在指标库注册：标注"待确认"
  - 统计维度：从 MRD 提取时间维度、组织维度、分析维度
  - 指标数据来源系统：从 MRD 的取数路径/来源系统提取
  - 系统取数后是否需要手工调整：根据 MRD 描述判断

#### 2. TP探源明细表
- 如已有标准数据模型，标注"非必填"
- 链接：[07 数据探源明细表](https://hisense.feishu.cn/wiki/FkRQwkBiAi0X7nkD4xrcIV1TnMh?fromScene=spaceOverview)

#### 3. 数据问题清单
- 链接：[06 数据问题清单](https://hisense.feishu.cn/wiki/LPIhw3gRgimAI2kxPnRcKU1an8b?fromScene=spaceOverview)

#### 4. 数据逻辑说明
- **来源**：MRD 的【1.4.1、1.4.2、1.4.3】复合指标逻辑 + 【1.4.4】取数路径
- **处理规则**：
  - 每个数据源/取数步骤单独一个子章节（数据1:、数据2、数据3...）
  - 每个子章节必须严格包含以下结构：

##### 子章节结构（严格按此格式输出）

```markdown
### 数据 N：

**业务逻辑：**（从 MRD 的【1.4.4】分步复制）

描述从哪个系统哪个表获取什么数据，筛选什么条件。

| 项目 | 适用工厂A（a工厂）、适用工厂B | 适用工厂C（如有差异） |
|------|------|------|
| 核心参与计算的页面字段名 | "字段1"、"字段2" | ········ |
| 页面其他重要字段 | "字段A"、"字段B"、"字段C" | |
| 来源 | 哪个系统，哪个页面（如：MOM-业务中心-现场管理查询-实时产量报表） | ········ |
| 页面截图 | （**必须**将MRD中的截图img链接直接插入此处，禁止写"见MRD"） | |
| 页面链接 | （如有则填写） | |
| 筛选条件 | 筛选条件1：①字段A = "值1" ②字段B = "值2" ③配置条件：字段C、字段D  时间维度 = 日/周/月  组织维度 = 线体 | |
| 特殊规则 | 如为空值如何处理、特殊过滤规则等 | |

/页面sql逻辑（如有）

**对应开发逻辑：**

【表名称】：对XX系统的XX表进行查询。
【筛选条件】：保留【字段A】=【字段B】的数据，且【字段C】="条件值"。
【取值】：取【字段1】、【字段2】字段信息。

**数据探源表：**（**必须包含**，不可省略。格式见下方说明）
```

  - **关键规则**：
    - 表格第一行表头中「适用公司/工厂」必须按 MRD 中实际涉及的工厂列出，如果不同工厂有差异则分列展示
    - 「核心参与计算的页面字段名」只填参与指标计算的核心字段
    - 「页面其他重要字段」填系统页面中需要取的其他列名称
    - 「来源」必须写清楚：哪个系统、哪个页面
    - 「筛选条件」必须结构化列出每个筛选项，并标注时间维度和组织维度
    - 「特殊规则」填写空值处理、特殊过滤、数据加工规则等
    - 如果 MRD 中没有提供某项信息，用 `⚠️ 待系统人员确认` 或 `🚨待补充` 标注
    - 「对应开发逻辑」如果 MRD 中有明确的表名、字段名、筛选条件则填写；否则标注"⚠️ 待系统人员确认"
    - **「数据探源表」强制规则**：每个数据子章节末尾必须包含数据探源表。格式为一个markdown表格，列出该数据源涉及的所有字段及其分类：

```markdown
**数据探源表：**

| 序号 | 字段名称 | 字段分类 | 说明 |
|------|---------|---------|------|
| 1 | 金额/数量等 | 度量值 | 需要汇总计算的核心数值字段 |
| 2 | 过账日期等 | 时间维度 | 时间相关字段 |
| 3 | 工厂/车间/线体等 | 组织维度 | 组织层级字段 |
| 4 | 物料号/凭证号等 | 辅助字段 | 其他需要取的字段 |
```

      如果MRD中没有提供足够信息来填写完整的探源表，则用以下格式占位并标注待补充：
```markdown
**数据探源表：** 🚨待补充（需确认各字段的度量值/维度分类）
```
      **绝对不可以省略数据探源表这一项。**

## 信息转换规则

### 可直接转换的内容（从 MRD 提取）
1. 需求提出人/部门
2. 业务背景（MRD 1.1）
3. 产品目标（MRD 1.3）
4. 指标名称和计算公式（MRD 1.4.1/1.4.2/1.4.3）
5. 统计维度（时间/组织/分析维度）
6. 数据来源系统
7. 业务逻辑描述（MRD 1.4.4 取数路径）
8. 统一口径定义

### 需要系统人员线下确认的内容
1. 具体数据库表名（如 hisense_mes_jd_db_user.pom_order）
2. 精确字段名（如 work_order_no, order_no）
3. SQL 筛选条件的精确写法
4. 指标是否已在指标库注册
5. 数据探源明细表内容
6. 系统取数后是否需要手工调整的具体规则

### 标注规范
- 已从 MRD 转换的内容：正常显示
- 需要系统人员确认的内容：用 `⚠️ 待系统人员确认：` 前缀标注
- MRD 中未提及的内容：用 `🚨待补充：` 前缀标注
- 开发人员填写的章节：用 `🟡🔧 开发填写` 标注

## 输出要求

1. 输出为飞书文档（通过 lark-cli 创建），不再生成本地 .md 文件
2. 内容使用飞书兼容的 Markdown 格式
3. 表格使用标准 markdown 表格语法
4. 仅在表格单元格内插入图片时使用 `<img src="..."/>` HTML 标签，其他场景不使用 HTML
5. 章节编号与模版保持一致
6. 所有"待确认"项集中在文档末尾再列一个清单，方便用户一次性找系统人员确认
7. **MRD 中的图片必须复制到 PRD 对应位置**（见下方图片处理规则）

## 图片处理规则（强制执行，不可遗漏）

**⚠️ 严禁在PRD中写"见MRD截图"或"见MRD"等占位文字。必须将MRD中的图片链接直接用 `<img src="..."/>` 标签插入到PRD对应的「页面截图」单元格中。**

当 MRD 文档中包含截图（如系统页面截图），必须将图片复制到 PRD 的对应表格单元格中：

### 提取方式
- 从 `lark-cli docs +fetch` 返回的内容中，找到 `<img>` 标签的 `href` 属性值（即图片的下载链接）
- 图片链接格式通常为：`https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=...`

### 插入方式
- 在表格单元格内使用 HTML img 标签：`<img src="图片href链接"/>`
- **必须使用 v2 API 写入**（`--api-version v2 --command overwrite`），v1 API 会丢失表格内的 img 标签
- 图片应放在「数据逻辑说明」表格的「页面截图」行对应单元格中
- 如果 MRD 中有多张截图，在同一单元格内用空格分隔多个 img 标签

### 写入飞书时必须使用 v2 API
- **写入内容命令**：`lark-cli docs +update --doc "<obj_token>" --api-version v2 --as user --command overwrite --content @./临时文件.md --doc-format markdown`
- **设置标题命令**（v2 overwrite 会清空标题，必须额外设置）：`lark-cli docs +update --doc "<obj_token>" --as user --mode append --markdown " " --new-title "<文档标题>"`
- **执行顺序**：先 v2 overwrite 写内容，再 v1 append 设标题
- **不要单独用 v1 API 的 `--mode overwrite`**，v1 API 会丢失图片和部分格式
- **图片链接有时效性**：飞书的 authcode 图片链接约1小时过期，必须在同一次操作中先 fetch MRD 获取最新链接，然后立即写入 PRD

### 示例
MRD 中的图片标签：
```
<img name="image.png" href="https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=XXXXX" .../>
```

PRD 中对应写法（表格单元格内）：
```markdown
| 页面截图 | <img src="https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=XXXXX"/> | |
```

## 输出文件末尾附加

在 PRD 文档最后附加一个汇总清单：
```markdown
---
## 📋 待确认事项汇总

| # | 待确认内容 | 对应章节 | 需确认人 |
|---|----------|---------|---------|
| 1 | ... | 二、数据定义 > 4.x | 系统人员 |
```

## 核心原则

1. **能从 MRD 提取的信息，必须完整提取并转换**，不能遗漏
2. **不确定的信息不要瞎编**，明确标注"待确认"
3. **PRD 是开发人员的执行文档**，信息必须具体、可操作
4. **保持与 MRD 的可追溯性**，标注信息来源章节
5. **输出格式要干净**，用户可以直接复制到飞书文档使用

## PRD 更新策略

- **默认局部更新**：当用户要求修改 PRD 中的某个部分时，只更新对应章节/段落，不重新生成整个文档。使用 v2 API 的 `str_replace` 或 `block_insert_after` 等局部操作命令。
- **整体重新生成**：仅当用户明确要求"重新生成整个 PRD"时，才用 `overwrite` 覆盖全文。
- **局部更新命令示例**：
  ```bash
  # 替换指定文本
  lark-cli docs +update --doc "<obj_token>" --api-version v2 --as user --command str_replace --pattern "<要替换的文本>" --content "<新内容>" --doc-format markdown
  
  # 在指定 block 后插入内容
  lark-cli docs +update --doc "<obj_token>" --api-version v2 --as user --command block_insert_after --block-id "<block_id>" --content "<新内容>" --doc-format markdown
  ```

# PRD 评审与优化工作流规范

## 触发条件

当用户提供一份已有的 PRD 文档要求"评审 PRD"、"看看 PRD 合不合格"、"帮我优化 PRD"时，按本工作流执行。

## 执行流程

1. 读取用户提供的 PRD 文档
2. 从 ETL 开发人员视角进行全面评审（评审维度见下方）
3. **先自动优化**：能直接改好的问题，直接在文档中修正（如格式问题、信息不完整但可从上下文推断的、逻辑表述不清晰但意思明确的）
4. **再列出待确认问题**：无法自行判断的问题，整理成问题清单输出给用户
5. 输出优化后的 PRD 文档 + 待确认问题清单

## 评审维度

从 ETL 开发人员"能否独立完成开发"的视角检查：

### 1. 结构完整性
- PRD 十大章节是否齐全
- 版本信息表是否存在
- 关联文档是否填写

### 2. 数据逻辑可执行性（最重要）
- 每个数据源是否有明确的：表名/系统路径、筛选条件、取值字段
- 开发逻辑是否具体到可以直接写 SQL 的程度
- 关联规则是否明确：关联字段名、关联方式（JOIN 类型）、匹配失败处理

### 3. 指标计算公式
- 公式是否有数学表达式
- 公式中的每个变量是否在取数路径中有对应定义
- 统一口径是否清晰无歧义

### 4. 信息一致性
- 各章节之间是否有矛盾（如口径和公式不一致、筛选条件前后不一致）
- 指标名称是否全文统一

### 5. 边界情况
- 空值/异常处理规则是否说明
- 数据缺失时的处理逻辑
- 时间边界（跨天、跨月）的处理

### 6. 度量值与展示逻辑
- 计算字段的公式是否完整
- 分类统计的枚举值是否完整
- 汇总逻辑是否明确

## 自动优化规则（直接改，不问用户）

以下问题直接在文档中修正：
1. **格式问题**：表格格式不规范、标题层级错误、标注符号不统一
2. **标注补全**：缺少 ⚠️/🚨/🟡🔧 标注的，按规范补上
3. **信息整理**：散落在各处的同类信息，整合到正确章节
4. **术语补充**：附录中缺少的术语定义，根据文档内容补充
5. **逻辑表述优化**：意思明确但表述不清晰的，改写为更清晰的表达
6. **重复内容去除**：同一信息重复出现的，保留最完整的版本
7. **开发逻辑格式化**：如果有表名、字段名等信息但没有按【表名称】【筛选条件】【取值】格式写的，帮忙格式化

## 不能自动优化的（列问题清单给用户）

以下问题必须列出来让用户确认或找人确认：
1. **业务逻辑不确定**：口径有歧义、公式有多种理解方式
2. **信息缺失**：完全没有提到的关键信息（表名、字段名、关联方式等）
3. **前后矛盾**：文档内两处描述互相矛盾，无法判断哪个正确
4. **边界规则缺失**：空值处理、异常处理等未说明
5. **枚举值不完整**：分类字段的可选值没有列全

## 输出格式

- 直接输出优化后的完整 PRD（覆盖原文件或新建文件）
- 优化过的地方用行内注释标注：`<!-- 已优化：原因 -->`

### 待确认问题清单（在聊天中输出）

格式如下：
```markdown
## 📋 PRD 评审待确认问题

| # | 问题 | 对应章节 | 我的建议 |
|---|------|---------|---------|
```

## 评审结论

在优化后的 PRD 文档顶部插入评审结论：
```markdown
> **📋 PRD 评审结果：✅ 合格 / ⚠️ 基本合格（有待确认项） / ❌ 不合格 | 评审日期：YYYY-MM-DD | 开发可执行度：XX%**
> 
> 结论描述
```

### 评判标准
- **✅ 合格**：开发可执行度 ≥ 90%，无🔴级问题，开发人员可直接开工
- **⚠️ 基本合格**：开发可执行度 60%-89%，有待确认项但不影响整体理解，确认后可开工
- **❌ 不合格**：开发可执行度 < 60%，关键信息大量缺失，无法开工

## 核心原则

1. **先优化再提问**：能改的先改好，减少用户来回沟通次数
2. **问题要具体**：不要问"请补充关联规则"，要问"APS表的线体字段叫什么名字？MES表的线体字段叫什么名字？"
3. **给出建议**：每个问题尽量附带你的建议或猜测，用户只需要确认"对/不对"
4. **区分确认人**：明确标注哪些问题用户自己能答，哪些需要找系统人员
