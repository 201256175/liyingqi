# MRD 评审工作流规范

## 评审流程

当用户提供 MRD 文档路径要求评审时，按以下流程执行：

1. 读取 MRD 文档（.md 文件）
2. 从 ETL 开发人员视角进行全面评审
3. **必须将评审结果回标到原始 .md 文件中**（不仅仅是在聊天中输出）
4. 同时在聊天中给出评审摘要

## 回标规范

### 文件顶部
在文件最开头插入评审总结论引用块：
```markdown
> **📋 MRD 评审结果：✅ 通过 / ❌ 不通过 | 评审日期：YYYY-MM-DD | ETL 信息覆盖度：XX%**
> 
> 总结论描述
```

### 章节标记
在每个可评审章节标题后添加标记：
- ✅ 该章节评审通过
- ❌ 该章节评审不通过
- ☐ 该章节未填写/待评审

### 问题批注
在对应章节下方用引用块插入具体问题：
```markdown
> **🔴 评审问题 #N：问题标题**（错误级别，必须修改）
> - 问题描述
> - 🔧 建议：修改建议

> **🟡 评审问题 #N：问题标题**（警告级别，建议修改）
> - 问题描述
> - 🔧 建议：修改建议

> **💡 评审问题 #N：问题标题**（建议级别，可选优化）
> - 问题描述
> - 🔧 建议：修改建议
```

### 文件底部
在文件末尾插入 ETL 开发信息缺口清单：
```markdown
> ## 📊 ETL 开发信息缺口清单
> 
> | # | 缺失信息 | 影响环节 | 建议补充内容 |
> |---|----------|----------|-------------|
> | 1 | ... | 取数/加工/关联/输出 | ... |
```

## 评审维度

从 ETL 开发人员视角检查以下内容：
1. **必填项完整性**：需求背景、需求目标、效率提升、指标计算公式、统一口径、取数路径、关联规则
2. **指标计算公式**：是否有数学表达式、变量是否在取数路径中有定义
3. **数据取数路径**：页面链接、精确字段名、来源系统、筛选条件
4. **数据关联规则**：关联字段、关联方式（JOIN 类型）、跨系统映射
5. **指标统一口径**：是否清晰、是否与公式一致
6. **ETL 信息完整性**：MRD 是 ETL 开发的唯一信息来源，必须包含 100% 开发所需信息
7. **空值/异常处理**：边界情况的处理规则

## 语言风格要求（重要）

回标到 MRD 文件中的问题描述和修改建议，必须站在海信集团产品公司业务人员的角度来写：

1. **不要使用 IT/ETL 专业术语**：不要说"JOIN 方式"、"数据库字段名"、"正则表达式"等技术词汇。业务人员看不懂。
2. **用业务语言替代技术语言**：
   - ❌ "补充 LEFT JOIN 关联方式" → ✅ "请说明两张表是怎么对应的，比如：用'订单号'把计划表和实际产量表对上"
   - ❌ "补充数据库字段名" → ✅ "请把系统里每一列的名称写清楚，比如截图中标红的那几列叫什么名字"
   - ❌ "补充页面 URL" → ✅ "请把系统页面的网址链接贴上来，就是浏览器地址栏里的那串网址"
   - ❌ "空值处理规则" → ✅ "如果某条数据是空的（没有值），应该怎么处理？是当作 0 算，还是直接跳过不算？"
3. **多举例说明**：每个修改建议尽量附带一个具体的例子，让业务人员一看就知道该怎么改。
4. **语气亲切**：用"请""建议""麻烦"等礼貌用语，不要用命令式口吻。
5. **ETL 信息缺口清单**中的"影响环节"列也要用业务语言：
   - "取数" → "从系统里取数据"
   - "加工" → "数据计算和处理"
   - "关联" → "多张表对应匹配"
   - "输出" → "最终报表展示"

## 核心原则

**MRD 文档是 ETL 开发人员的唯一信息来源。** 评审必须确保仅凭 MRD 文档中的信息，ETL 开发人员能够 100% 独立完成指标开发工作。任何信息缺口都必须在评审阶段被识别并要求补充。
