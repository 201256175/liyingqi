# MRD 评审工作流规范

## 输出路径规范

- MRD 评审结果文档统一输出到飞书 Wiki，作为被评审 MRD 文档的子文档
- 文件命名格式（飞书文档标题）：`{原MRD文件名}-评审版`
- **不再生成本地 .md 文件**

## 飞书输出规范

### 评审结果文档创建位置
- **位置**：在用户提供的 MRD 飞书链接下面创建子文档
- 先获取 MRD 的 node_token，然后在其下创建子节点

### 创建飞书评审文档命令
```bash
# 第一步：获取 MRD 文档的 wiki node 信息
lark-cli wiki +node-get --node-token "<MRD飞书链接>" --as user --format pretty

# 第二步：在 MRD 节点下创建评审结果子文档
lark-cli wiki +node-create --title "{MRD标题}-评审版" --parent-node-token "<MRD的node_token>" --space-id "7497785984860553218" --as user

# 第三步：获取新创建文档的 obj_token，然后写入评审内容
lark-cli docs +update --doc "<新文档的obj_token>" --api-version v2 --as user --markdown "<评审内容markdown>"
```

### 注意事项
- 所有 lark-cli 命令必须加 `--as user` 参数
- markdown 内容如果太长，可以先写入临时文件再用 `@file` 引用：`--markdown @./mrd_review_content.md`
- 创建文档后在聊天中告知用户飞书文档链接

### 文档更新规则（重要）
- **重新评审时不创建新文档**：如果该 MRD 下面已经有评审文档，必须在原文档基础上修改更新（用 `lark-cli docs +update --mode overwrite`），不要重复创建新文档
- **版本号递增**：每次更新时版本号 +1（1.0 → 2.0 → 3.0...）
- **变更描述**：在版本记录表/评审结论中写清楚本次变更了什么内容（如"根据MRD v2.0更新重新评审"）
- **查找已有文档**：更新前先用 `lark-cli wiki +node-list` 或 `+node-get` 检查 MRD 下面是否已有评审子文档，有则更新，无则新建

### 规则

- **每完成一个阶段**，输出一次更新后的完整面板
- 「说明」列简要写该阶段的关键产出或状态
- 完成时在「说明」列附上飞书文档链接
- 如果用户只要求"评审MRD"不生成PRD，则只显示①②③（进度条按3阶段算百分比）
- 如果用户只要求"生成PRD"不评审，则只显示①④⑤⑥（进度条按4阶段算百分比）
- 如果用户要求"评审MRD并生成PRD"，则显示完整的①~⑥
- 失败时标记 ❌ 并在说明列写原因，然后自动重试或提示用户

## 评审流程

当用户提供 MRD 飞书链接要求评审时，按以下流程执行：

1. 用 `lark-cli docs +fetch --doc "<飞书链接>" --api-version v2 --as user --format pretty` 读取 MRD 文档
2. 从 ETL 开发人员视角进行全面评审
3. **必须将评审结果创建为飞书新文档**，放在 MRD 文档下面作为子文件
4. 同时在聊天中给出评审摘要和新文档链接

## 评审维度

从 ETL 开发人员视角检查以下内容：
1. **必填项完整性**：需求背景、需求目标、效率提升、指标计算公式、统一口径、取数路径、关联规则
2. **指标计算公式**：是否有数学表达式、变量是否在取数路径中有定义
3. **数据取数路径**：前台页面路径、页面中的字段名称、来源系统、筛选条件
4. **字段分类明确性（🔴重点检查）**：MRD 必须明确标注每个字段的角色分类，具体要求如下：
   - **度量值字段（最重要）**：哪些字段是需要计算/汇总的数值（如产量、金额、数量、工时等）。这是报表的核心，必须写清楚。如果MRD没有明确哪些是度量值，标为🔴错误级别。
   - **时间维度字段**：哪些字段代表时间（如过账日期、生产日期、记账日期等），以及最小时间粒度（日/周/月）
   - **组织维度字段**：哪些字段代表组织层级（如工厂、车间、线体、班组等），以及最小组织粒度
   - **其他重要字段**：除度量值和维度外，还需要取的辅助字段（如物料号、凭证号、用户名等）
   - 评审时如果MRD只笼统写了"取这些字段"但没有区分哪些是度量值、哪些是维度，必须提出🔴错误级别的评审问题，要求业务方明确分类。
5. **数据关联规则**：关联字段、关联方式（JOIN 类型）、跨系统映射
6. **指标统一口径**：是否清晰、是否与公式一致
7. **ETL 信息完整性**：MRD 是 ETL 开发的唯一信息来源，必须包含 100% 开发所需信息
8. **空值/异常处理**：边界情况的处理规则

**MRD 阶段不要求的内容（不作为🔴错误级别）：**
- 后台数据库表名：MRD 阶段业务方不需要写后台表名，只需写清楚从哪个前台页面取哪些字段。如果缺少后台表名，最多作为🟡警告级别（建议填写），不能标为🔴错误。
- 精确的数据库字段英文名：同上，MRD 阶段用页面上的中文字段名即可。

## 语言风格要求（重要）

回标到 MRD 文件中的问题描述和修改建议，必须站在海信集团产品公司业务人员的角度来写：

1. **不要使用 IT/ETL 专业术语**：不要说"JOIN 方式"、"数据库字段名"、"正则表达式"等技术词汇。业务人员看不懂。
2. **用业务语言替代技术语言**：
   - ❌ "补充 LEFT JOIN 关联方式" → ✅ "请说明两张表是怎么对应的，比如：用'订单号'把计划表和实际产量表对上"
   - ❌ "补充数据库字段名" → ✅ "请把系统里每一列的名称写清楚，比如截图中标红的那几列叫什么名字"
   - ❌ "补充页面 URL" → ✅ "请把系统页面的网址链接贴上来，就是浏览器地址栏里的那串网址"
   - ❌ "空值处理规则" → ✅ "如果某条数据是空的（没有值），应该怎么处理？是当作 0 算，还是直接跳过不算？"
3. **多举例说明**：每个修改建议尽量附带一个具体的例子，让业务人员一看就知道该怎么改。
4. **语气亲切**：用"请""建议""麻烦"等礼貌用语，不要用命令式口吻。
5. **ETL 信息缺口清单**中的"影响环节"列也要用业务语言：
   - "取数" → "从系统里取数据"
   - "加工" → "数据计算和处理"
   - "关联" → "多张表对应匹配"
   - "输出" → "最终报表展示"

## 核心原则

**MRD 文档是 ETL 开发人员的唯一信息来源。** 评审必须确保仅凭 MRD 文档中的信息，ETL 开发人员能够 100% 独立完成指标开发工作。任何信息缺口都必须在评审阶段被识别并要求补充。
